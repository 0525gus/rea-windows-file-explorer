# REA 기반 Windows 파일 탐색기 역공학 및 크로스플랫폼 재구현 PoC

**프로젝트명:** REA Explorer Reconstruction

**프로젝트 유형:** AI 기반 소스코드 비공개 역공학 및 소프트웨어 재구현 실험

**주요 기술:** C++20, Qt6, CMake, REA MCP, Ghidra, Codex

## 1. 프로젝트 목적

### 1.1 최종 목표

REA(Reverse Engineer Anything)를 활용해 기존 Windows 파일 탐색기 프로그램의 실행파일을 역공학하고, 분석 결과를 바탕으로 원본의 주요 기능과 동작을 충실하게 재구현한다.

최종 애플리케이션은 Windows 11 파일 탐색기와 유사한 UI 및 사용 경험을 제공하면서 Windows, Linux, macOS에서 공통 코드베이스를 재사용할 수 있도록 설계한다.

### 1.2 핵심 검증 질문

1. REA는 소스코드 없이 실행파일의 내부 구조를 어느 수준까지 분석할 수 있는가?
2. AI 에이전트는 REA 분석 결과를 이용해 실제 기능을 얼마나 정확하게 복원하는가?
3. REA를 사용하지 않는 일반적인 AI 코딩 방식보다 어떤 이점이 있는가?
4. 원본의 Windows 전용 기능을 크로스플랫폼 구조로 재설계할 수 있는가?
5. 분석과 구현에 어떤 AI 모델, 컴퓨팅 리소스 및 비용이 필요한가?

프로젝트의 성공은 단순한 프로그램 완성이 아니라 실제 역공학 결과와 그 활용 효과를 입증하는 것으로 정의한다.

## 2. 분석 대상 및 제한 사항

### 2.1 분석 대상

- **대상 프로그램:** Explorer++
- 공식 프로젝트: https://github.com/derceg/explorerplusplus
- 분석 입력: 공식 배포 실행파일 및 실행 중 관찰할 수 있는 동작
- 우선 대상: Windows x64 배포판
- UI 디자인 참고: Windows 11 File Explorer

분석할 실행파일의 정확한 버전, 다운로드 출처, SHA-256 해시를 기록한다.

### 2.2 원본 소스코드 접근 금지

역공학 실험 단계에서는 다음 행위를 금지한다.

- Explorer++의 원본 C++ 소스코드 열람
- GitHub 소스 저장소의 클론 및 코드 검색
- 기존 구현을 복사하여 프로젝트에 통합
- 공개된 역공학 결과를 분석 근거 없이 사용
- 원본 소스코드를 AI 에이전트의 컨텍스트에 제공

허용하는 자료는 다음으로 제한한다.

- 컴파일된 원본 실행파일 및 필요한 배포 파일
- 원본 프로그램을 직접 실행하여 관찰한 결과
- REA 및 Ghidra를 통해 추출한 분석 정보
- 운영체제 및 개발 프레임워크의 공식 API 문서

초기 구현 및 분석 보고서가 확정된 이후에만 원본 소스코드를 확인해 정확도를 검증한다.

실험 조건을 보장하기 위해 역공학과 검증 단계의 작업 디렉터리 및 접근 권한을 분리한다.

## 3. 개발 환경 구축

### 3.1 필수 개발 환경

| 구성 요소 | 요구사항 |
|---|---|
| 운영체제 | Windows 10/11 x64 |
| 언어 | C++20 |
| 컴파일러 | MSVC |
| GUI | Qt6 Widgets 또는 QML |
| 빌드 | CMake |
| AI 에이전트 | Codex |
| 역공학 프레임워크 | REA Skill + MCP |
| 바이너리 분석기 | Ghidra |
| 버전 관리 | Git |

### 3.2 REA 검증

실제 역공학 전에 다음을 검증한다.

1. REA MCP가 에이전트에 정상 등록되어 있는가?
2. 에이전트가 REA 분석 도구 목록을 확인할 수 있는가?
3. Ghidra 실행 경로와 JDK 구성이 유효한가?
4. 작은 Windows PE 실행파일을 분석할 수 있는가?
5. 함수 정보, 호출 관계, 디컴파일 결과를 실제로 얻을 수 있는가?
6. 분석 결과를 파일에 저장하고 재검토할 수 있는가?

**MCP 연결 성공만으로 분석 환경이 정상이라고 판단하지 않는다.** 실제 분석 도구 호출과 결과 확인까지 완료해야 한다.

환경 또는 지원 기능에 문제가 있다면 원인을 기록하고, 해당 기능을 수행하지 못한 상태로 보고한다.

## 4. REA 역공학 요구사항

### RE-01. 바이너리 구조 분석

다음 항목을 확인한다.

- 실행파일 형식 및 아키텍처
- PE 헤더와 섹션 구성
- Import/Export 정보
- 문자열 및 리소스
- 함수 목록과 진입점
- 호출 관계 및 외부 API 의존성

결과: `docs/analysis/binary-overview.md`

### RE-02. 파일 탐색 로직 분석

폴더를 선택했을 때 화면에 파일이 표시되는 과정을 추적한다.

필수 분석 항목:

- 폴더 경로 전달 방식
- 디렉터리 열거 로직
- 파일 속성 및 메타데이터 조회
- 파일 목록 갱신
- 파일 정렬 방식
- 디렉터리 접근 실패 처리

관련 함수 및 호출 관계를 분석해 다이어그램으로 정리한다.

### RE-03. 사용자 이벤트 처리 분석

다음 이벤트의 처리 흐름을 추적한다.

- 폴더 더블클릭
- 상위 폴더 이동
- 뒤로 가기 및 앞으로 가기
- 새 탭 생성
- 파일 선택
- 파일 이름 변경
- 검색 실행

UI 이벤트와 내부 로직이 연결되는 방식을 조사한다.

### RE-04. Windows Shell 연동 분석

Windows에서 제공하는 기능을 어떻게 사용하는지 확인한다.

예시:

- 파일 아이콘 및 썸네일
- 파일 연결 프로그램 실행
- 디렉터리 변경 감지
- 파일 복사 및 이동
- 드래그 앤 드롭
- 파일 속성 표시
- 휴지통 처리

모든 기능을 자체 구현한다고 가정하지 않는다. Windows가 제공하는 API를 재사용한 부분과 원본 프로그램의 고유 로직을 구분한다.

### RE-05. 분석 증거 보존

주요 분석 결과마다 다음 정보를 저장한다.

- 분석 대상과 바이너리 해시
- 사용한 REA 도구 및 분석 엔진
- 조사 목적
- 관련 함수 주소 또는 식별자
- 디컴파일 결과 및 참조 정보
- 추론 과정과 결과
- 분석 신뢰도
- 아직 확인되지 않은 사항

분석 근거가 불충분한 내용은 확정된 사실로 기록하지 않는다.

| ID | 기능 | 세부 요구사항 |

### 5.3 P2 — 고급 기능

- 썸네일 및 파일 미리보기

- 복사·이동 작업 취소
- Undo/Redo
- 다크 모드
- 사용자 설정 저장
- Windows Shell 특수 위치 지원

P2는 시간과 분석 가능 범위에 따라 구현한다. 구현하지 못한 항목을 완료로 표시하지 않는다.

## 6. UI 및 사용자 경험

### 6.1 디자인 기준

UI는 Windows 11 파일 탐색기의 현대적인 디자인을 참고하되, 원본 Explorer++의 기능 동작과 분리하여 설계한다.

기본 레이아웃:

1. 상단 탭 바
2. 탐색 버튼 및 주소 표시줄
3. 좌측 디렉터리 트리
4. 중앙 파일 목록
5. 검색 입력창
6. 하단 상태 표시줄

### 6.2 사용자 경험 요구사항

- 마우스와 키보드 모두 지원
- 창 크기 변경 시 레이아웃 정상 반응
- 폴더 탐색 중 UI 멈춤 방지
- 긴 파일 이름 및 Unicode 지원
- 대량 파일 목록 처리 중 진행 상태 제공
- 오류 발생 시 복구 가능한 안내 메시지 표시
- Windows 스타일에 맞는 기본 아이콘 및 포커스 동작

Windows의 저작권 보호 대상 UI 자산을 무단 추출해 포함하지 않으며, 허용된 OS 리소스 또는 별도로 제작한 디자인 자산을 사용한다.

### 6.3 GUI 기술 선택

Qt6 Widgets 또는 QML을 비교한 뒤 하나를 결정한다.

선정 기준:

- Windows 탐색기형 UI 재현성
- 개발 난이도
- 성능 및 메모리 사용
- 사용자 정의 UI 유연성
- 크로스플랫폼 동작
- 유지보수성

선정 이유를 ADR(Architecture Decision Record)로 작성한다.

## 7. 소프트웨어 아키텍처

### 7.1 기본 원칙

**UI, 공통 비즈니스 로직, OS 종속 기능을 분리한다.**

권장 계층:

| 계층 | 책임 |
|---|---|
| Presentation | Qt6 기반 UI |
| Application | 탐색·검색·파일 작업 오케스트레이션 |
| Domain | 경로, 항목, 탐색 기록, 파일 작업 모델 |
| Platform Interface | OS 독립 인터페이스 |
| Platform Adapter | OS별 파일 시스템 및 Shell 연동 |

### 7.2 공통 코어

Windows, Linux, macOS에서 재사용할 기능은 공통 C++20/Qt Core로 구현한다.

- 경로 및 탐색 기록 관리
- 탭 상태 관리
- 검색 결과 관리
- 정렬 및 필터 로직
- 파일 작업 요청 처리
- 작업 진행 상태
- 오류 모델 및 사용자 메시지

### 7.3 OS별 어댑터

OS에 종속되는 기능은 분리한다.

**Windows**
- Win32 API
- Windows Shell API
- COM 인터페이스

**Linux**
- 표준 파일 시스템 API
- 필요한 경우 GIO 등 플랫폼 통합 기능

**macOS**
- 표준 파일 시스템 API
- 필요한 경우 Foundation/AppKit 기반 통합 기능

공통 비즈니스 로직이 Win32 함수에 직접 종속되지 않도록 한다.

### 7.4 아키텍처 검증

- OS 종속 호출이 지정된 Adapter 외부에 무분별하게 존재하지 않아야 한다.
- 플랫폼별 기능은 지원 여부를 질의할 수 있어야 한다.
- 지원하지 않는 기능은 명시적 오류를 반환해야 한다.
- 공통 코어는 실제 OS 환경 없이 모의 어댑터로 테스트할 수 있어야 한다.
- Windows 전용 기능이 다른 OS의 빌드를 방해하지 않아야 한다.

## 8. 비기능 요구사항

### NFR-01. 성능

- 디렉터리 로딩은 비동기 처리를 우선한다.
- 대량 파일 조회 중 메인 UI 스레드가 장시간 차단되지 않아야 한다.
- 파일 복사·이동 진행 상태를 표시한다.
- 메모리 및 CPU 사용량을 측정한다.
- 원본 Explorer++와 동일 조건에서 비교한다.

성능 목표값은 사전 테스트 환경을 정의한 뒤 기준값으로 확정한다.

### NFR-02. 안정성

- 접근할 수 없는 디렉터리에서도 프로그램이 종료되지 않아야 한다.
- 파일 작업 실패 시 원인을 표시한다.
- 파일이 외부 프로그램에 의해 변경되거나 삭제되는 상황을 처리한다.
- 경로 길이, Unicode, 심볼릭 링크 및 Windows 재분석 지점(reparse point)을 고려한다.
- 심볼릭 링크 순환으로 무한 탐색이 발생하지 않아야 한다.

### NFR-03. 파일 안전성

- 초기 테스트는 별도의 테스트 디렉터리에서 수행한다.
- 원본 시스템 파일 및 사용자 중요 데이터를 자동으로 삭제하거나 변경하지 않는다.
- 덮어쓰기, 영구 삭제처럼 파괴적인 작업에는 확인 절차를 둔다.
- 복사 실패 시 원본 파일은 보존되어야 한다.
- 경로 및 접근 권한 검사 실패를 무시하지 않는다.

### NFR-04. 유지보수성

- CMake 기반 재현 가능한 빌드 제공
- 공개 인터페이스 문서화
- 모듈별 책임 구분
- 자동화 테스트 작성

- 외부 라이브러리 및 라이선스 목록 관리

## 9. REA 효과 검증 실험

### 9.1 비교 실험

최소한 두 개발 방식을 비교한다.

| 구분 | 실험 A | 실험 B |
|---|---|---|
| AI | 동일한 모델 | 동일한 모델 |
| 입력 | 실행파일·관찰 결과 | 실행파일·관찰 결과 |
| REA | 미사용 | 사용 |
| 원본 소스코드 | 열람 금지 | 열람 금지 |
| 개발 환경 | 동일 | 동일 |
| 기능 요구사항 | 동일 | 동일 |

실험 A에서는 REA 분석 결과를 제공하지 않으며, 실험 B에서는 실제 확보한 분석 결과를 활용한다.

가급적 두 실험을 독립된 작업 디렉터리와 에이전트 세션에서 수행한다.

### 9.2 측정 지표

| 지표 | 측정 방식 |
|---|---|
| 기능 구현률 | 요구 기능 중 정상 동작한 기능 비율 |
| 동작 일치율 | 원본과 동일한 테스트 결과를 보인 비율 |
| 역공학 정확도 | 사후 원본 소스와 분석 결과 비교 |
| 개발 시간 | 각 단계의 실제 작업 시간 |
| AI 비용 | 입력·출력 토큰과 API 비용 |
| 분석 성공률 | 조사 질문 중 근거를 확보한 비율 |
| 안정성 | 예외 상황 테스트 통과율 |
| 이식성 | OS별 빌드 및 기능 테스트 결과 |

### 9.3 REA 기여도 평가

각 기능의 구현 과정을 다음 중 하나로 분류한다.

- **REA 근거 기반:** 역공학에서 확인한 내부 동작을 구현에 활용
- **일반 API 기반:** 공식 운영체제 문서 및 표준 API로 구현
- **AI 추론 기반:** 직접적인 역공학 근거 없이 추론하여 구현
- **미구현:** 요구 기능 구현에 실패

단순히 Qt가 제공하는 파일 시스템 모델을 사용해 만든 기능을 REA가 복원한 기능이라고 주장하지 않는다.

## 10. 테스트 및 검증

### 10.1 기능 테스트

다음 시나리오는 필수 테스트한다.

1. 빈 폴더 열기
2. 파일 1,000개 이상 포함된 폴더 열기
3. 한글 및 특수문자 파일 이름 처리
4. 존재하지 않는 경로 접근
5. 권한이 없는 폴더 접근
6. 뒤로/앞으로 탐색 기록
7. 여러 탭의 독립적인 경로 유지
8. 이름·크기·수정일 정렬
9. 검색 결과의 정확성
10. 파일 복사·이동 중 중복 파일 충돌
11. 파일이 실행 중 외부에서 삭제되는 상황
12. 파일 또는 폴더 이름 변경 실패
13. 심볼릭 링크 및 순환 경로 처리
14. 앱 종료 및 재실행 시 안정성

읽기 기능과 파일 수정 기능은 테스트 범위를 분리한다.

### 10.2 역공학 검증

실제 분석 대상 기능마다 다음을 비교한다.

- REA가 찾은 함수와 호출 관계
- 관찰된 실제 프로그램 동작
- 재구현 프로그램 동작
- 최종 단계에서 확인한 원본 소스코드 구조

디컴파일된 의사코드를 원본 코드와 동일한 것으로 간주하지 않는다.

### 10.3 플랫폼 테스트

**Windows**
- 실제 빌드
- 실제 실행
- 기능 테스트
- 배포 패키지 실행 확인

**Linux**

- 공통 기능 및 어댑터 테스트
- 플랫폼별 제한 기록

**macOS**

- 빌드 환경이 확보되면 실행 테스트

## 13. 최종 완료 기준

프로젝트가 완료되었다고 판단하려면 다음 조건을 충족해야 한다.

- [ ] REA MCP 및 Ghidra를 실제로 사용한 분석 기록이 존재한다.
- [ ] 초기 역공학과 구현 과정에서 원본 소스코드를 사용하지 않았다.
- [ ] C++20/Qt6 기반 Windows 애플리케이션이 정상 빌드된다.
- [ ] P0의 모든 기능 테스트가 통과한다.
- [ ] 주요 기능에 대한 원본과 재구현 결과 비교가 존재한다.
- [ ] UI, 공통 코어, OS별 어댑터가 분리되어 있다.
- [ ] 공통 코드의 크로스플랫폼 이식 가능성을 검토했다.
- [ ] Linux 실행 검증 여부와 결과를 명확히 기록했다.
- [ ] REA 분석 근거와 AI 추론을 구분했다.
- [ ] AI 모델·리소스·개발 시간·비용을 보고했다.
- [ ] 남은 문제와 미구현 기능을 명시했다.

검증되지 않은 기능을 성공으로 처리하지 않는다.

## 14. 에이전트 작업 지침

1. 요구사항을 기준으로 개발 계획을 수립한다.
2. 현재 환경을 검사하고 실행 가능한 단계부터 진행한다.
3. 역공학 도구를 실제로 호출하고 결과를 기록한다.
4. 개발 중 기능별 구현 및 테스트 결과를 지속적으로 갱신한다.
5. 프로젝트 범위를 임의로 축소하거나 요구사항을 삭제하지 않는다.
6. 외부 소프트웨어 설치, 시스템 변경 및 위험한 파일 작업은 사전 승인을 받는다.
7. 분석 실패 시 실패 원인을 남기고 복구 방안을 검토한다.
8. 원본 소스코드 없이 구현한 사실을 검증 가능하게 유지한다.
9. 각 단계 완료 후 다음 단계의 입력 자료와 미해결 문제를 명시한다.
10. 완료 조건을 충족하지 못한 항목은 정직하게 미완료로 보고한다.

**최종 목표: 소스코드가 없는 실행파일로부터 REA와 AI 에이전트를 활용해 실제 데스크톱 소프트웨어를 역공학·재구현하고, 그 정확도와 개발 생산성에 미치는 영향을 정량적으로 검증한다.**
