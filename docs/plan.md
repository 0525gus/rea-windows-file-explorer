# REA Explorer Reconstruction 실행 계획

기준: [`requirements.md`](requirements.md) 전체. 세부 추적과 현재 판정은 [`evaluation/requirements-matrix.md`](evaluation/requirements-matrix.md)에 유지한다. 작성 시각 기준은 2026-10-21 Asia/Seoul이다. 이 계획에 적힌 명령·실험·산출물은 실제 실행 전까지 완료 근거가 아니다.

현재 상위 작업자의 실제 실행 보고에 따르면 REA 서버 6.7.0/Ghidra 12.1.4/Java 21.0.12.1 환경에서 작은 `whoami.exe` PE의 함수·호출·비어 있지 않은 의사코드를 확보했다. 4기록/129,899바이트 bundle을 저장·JSON 재파싱했고 세션 정본은 [`analysis/evidence/phase1-session.json`](analysis/evidence/phase1-session.json)에 있다. 함수 341개·문자열 308개를 보고한 overview 및 진입 함수 `0x140001cb0`의 두 호출 대상을 포함하는 함수 분석 Evidence는 매트릭스에 식별자를 기록했다. 작은 PE 기술 게이트는 통과했다.

공식 x64 Explorer++ `1.4.0.2293` 배포 실행파일/라이선스만 확보했으며 SHA-256은 `22ac20341c5525658ebe5e9c4b9ac9f7c152b18080ff347861fac3f04d56a2d6`이다. [`analysis/target-manifest.json`](analysis/target-manifest.json)에 출처/해시가 있고 대상 초기 Ghidra 분석이 진행 중이다. [`analysis/clean-room.md`](analysis/clean-room.md)가 작성되었으나 ACL/권한 분리와 Git 초기화는 남아 있다. MSVC/CMake 존재, Windows Qt 한정 검색에서 미발견, WSL Qt 존재가 보고되었다. 원본 GUI 관찰·구현·앱 빌드·벤치마크는 미완료이다. 현재 목표 턴은 실제 PE 분석 근거와 재검토 기록, 대상 확보 및 요구사항 추적 문서로 실질 진전이 있었다.

## 실험 경계와 작업 통제

1. Phase 1부터 순차 진행한다. 각 게이트는 실제 자료로 판정하고 다음 단계에 입력·미해결 문제를 명시한다. 실패한 분석은 실패 사유와 가능한 복구를 기록한다.
2. 초기 역공학·구현·분석 보고서 확정 전에는 Explorer++ 원본 C++ 코드, 저장소 클론/코드 검색, 기존 구현, 근거 없는 공개 역공학 결과를 보거나 컨텍스트에 넣지 않는다. 공식 GitHub의 배포 메타데이터/실행파일을 얻는 작업은 소스 트리 탐색과 구별한다.
3. 허용 자료는 컴파일된 공식 배포물, 직접 실행 관찰, 실제 REA/Ghidra 자료, OS/개발 프레임워크 공식 API 문서이다. 자료의 URL·경로·해시·용도를 기록하고 허용 범위를 넘는 링크는 열지 않는다.
4. 초기 작업 영역과 최종 소스 검증 영역은 작업 디렉터리뿐 아니라 실제 접근 권한도 분리한다. 검증 영역은 초기 구현·분석 보고서와 freeze manifest를 고정하기 전까지 비어 있게 유지하고 원본 소스를 다운로드하지 않는다. 역공학 세션이 사후 검증 소스를 읽을 수 없어야 한다. 경로 이름만 나눈 것을 권한 분리라고 보고하지 않는다. 적합한 계정/ACL/세션 통제가 필요한 경우 구체적인 변경 계획과 승인을 먼저 준비한다.
5. 외부 소프트웨어 설치, 시스템 변경, 위험한 파일 작업은 요구사항 §14.6의 사전 승인을 따른다. 먼저 읽기 전용 환경 점검으로 필요한 조치를 특정한다. 일반 개발·분석 승인에서 설치 승인을 추정하지 않는다.
6. 원본 앱 실행과 재구현 파일 작업은 별도 소유 fixture에서만 수행한다. 실제 중요 데이터·시스템 파일을 자동 변경/삭제하지 않는다. 덮어쓰기·영구 삭제에는 앱 자체 확인 절차를 둔다. fixture 정리도 소유권·정확 경로 확인 후 수행한다.
7. 관찰, 도출, 추론, 미확인을 분리한다. 실제 REA 근거 없이 구현한 Qt/표준 API 기능은 `일반 API 기반` 또는 `AI 추론 기반`이다. 기능 구현과 역공학 성공을 별개로 평가한다.
8. 결과는 호출 원문과 재검토 가능한 Evidence를 먼저 저장하고 요약 문서에서 링크한다. 명령 인자·선택 입력·대상 해시·세션·도구/엔진·신뢰도·분석 한계를 유지한다.

## 공통 기록 및 A/B 준비

권장 기록 산출물은 `docs/analysis/environment.md`, `target-manifest.md`, `calls/`, `evidence/`, `observations.md`, `behavior-map.md`, `binary-overview.md`, `docs/architecture/`, `docs/evaluation/experiment-protocol.md`, `measurements/`, `results.md`, `limitations.md`이다. 아직 이 파일들은 생성/검증되었다고 주장하지 않는다.

실험 A와 B는 동일한 실제 모델 식별자, 요구사항, Windows 환경/개발 도구, 공식 실행파일 해시, 공통 관찰 시나리오/자료, 테스트 fixture·판정·범위를 사용한다. A는 REA 도구와 REA 분석 결과를 제공받지 않고, B만 실제 분석 결과를 사용한다. 가능하면 별도 디렉터리, 독립 에이전트 세션과 읽기 권한으로 통제하며 A는 B의 코드·설계·메모·Evidence에 접근하지 못하게 한다. REA 결과를 이미 본 세션을 A로 재사용하지 않는다.

독립 모델 세션을 실제로 제공할 수 있는지 Phase 1에서 확인한다. A의 입력은 공통 요구·실행파일·직접 관찰과 공식 API 문서만으로 준비한다. 한 세션의 모델 기억을 지웠다고 주장하여 독립성을 대신하지 않는다. 동일 모델이나 독립 컨텍스트를 확인할 수 없다면 요구된 비교는 미완료로 남기고 대체 비교의 제약을 공개한다. A/B 모두 최종 소스 검증 전 독립 산출물을 고정한다. A의 범위를 B보다 줄이지 않는다.

프로토콜에 기록할 측정값:

- 기능 구현률: 우선순위별 고정 요구 기능 중 실제 테스트 통과 기능/전체 요구 기능. 미실행을 통과로 넣지 않는다.
- 동작 일치율: 원본과 동일 결과인 사전 고정 비교 테스트/비교 대상 테스트. 미검증·미지원·제외 항목과 분모를 공개한다.
- 역공학 정확도: 소스 확인 전에 고정한 주장과 사후 원본 구조를 비교하여 확인/오류/미확인으로 분리한다.
- 분석 성공률: 사전 조사 질문 중 실제 근거 확보 질문/전체 질문. 단순 호출 성공률과 구별한다.
- 개발 시간: 단계별 실제 시작·종료·중단·작업/대기 시간. 이미 기록하지 못한 기간은 미측정이다.
- AI: 모델 실제 식별자·설정, 입력/출력/기타 실제 제공 토큰, 호출 수, API 가격 기준·통화·비용. 접근 불가 값은 미측정으로 남기고 추정은 명시한다.
- 리소스/성능: 같은 하드웨어·OS·데이터셋·동작·캐시 조건에서 원본/A/B의 elapsed, CPU time, peak process-family memory. cold/warm을 구분하고 측정 도구·샘플 간격·포함 프로세스·제외 비용을 남긴다.
- 안정성: 예외 시나리오 실제 통과/실행 대상과 실제 권한·링크 제한. 모의 어댑터와 실제 OS 결과를 혼동하지 않는다.
- 이식성: Windows/Linux/macOS 각각 빌드·실행·공통/어댑터 테스트·패키지 여부와 환경 부재/미검증.

사전 환경과 기준값을 정의한 후 성능 목표를 확정한다. 응답 바이트 감소를 토큰 감소나 성능 개선으로 대체하지 않는다. 숫자를 얻을 수 없는 비용은 0으로 쓰지 않는다.

## Phase 1 — 환경 구축과 실제 PE 검증

수행 순서:

1. Windows 버전/x64, MSVC·C++20, Qt6, CMake, Git, Codex 모델/세션, REA Skill/MCP, Ghidra/JDK 경로·버전을 읽기 전용으로 확인한다. 설치·설정 변경이 필요한 항목만 따로 보고한다.
2. 적용 REA Skill을 읽고 실제 도구 목록을 조회한다. 도구의 지원 계약에 따라 작은 Windows PE 분석에 필요한 최소 호출을 선택한다.
3. 작은 합법적 PE fixture의 출처/해시를 고정하고 REA/Ghidra로 분석한다. 실제 함수 목록/진입점, 호출 관계, 의사코드를 얻고 파일에 보존한다. 보존된 출력을 다시 열어 검토한다. 실패한 엔진/기능과 복구 시도를 기록한다.
4. 공식 Explorer++ Windows x64 배포물을 소스 없이 확보한다. 정확 버전·릴리스/asset URL·파일명·크기·SHA-256·서명 확인 가능 여부를 manifest에 기록한다. 해시가 같지 않으면 동일 대상이라고 주장하지 않는다.
5. clean-room 디렉터리/권한과 A/B 독립 세션 가능성을 확인한다. 관찰용 fixture와 기록·시간/리소스 측정 체계를 준비한다.

게이트: 실제 REA 함수·의사코드 분석 성공, 호출 관계 확인, 보존·재검토 증거가 있어야 한다. 연결 응답만으로 통과하지 않는다. 대상 확보·해시와 전체 환경 미해결 사항도 Phase 1 산출물로 남긴다.

Phase 2 전달: 환경 inventory, 작은 PE 분석 근거/한계, 공식 대상 manifest, clean-room 통제·A/B 준비 상태, 미설치 도구나 미확인 기능 목록.

## Phase 2 — 원본 관찰과 REA 기반 조사

1. Explorer++를 격리 fixture에서 실제 실행하고 원본 버전/해시·창 크기·OS 조건·동작을 기록한다. P0 전부와 필수 14시나리오를 기준으로 공통 관찰 자료를 만든다. P1·Shell 동작도 분석 계획에 포함한다.
2. RE-01: 형식/아키텍처·PE 헤더/섹션·import/export·문자열/리소스·함수/진입점·호출/외부 API를 실제 분석하여 `docs/analysis/binary-overview.md`를 작성한다.
3. RE-02: 폴더 선택부터 경로 전달→열거→메타데이터→목록 갱신→정렬→접근 실패 처리까지 함수와 호출 근거를 연결해 다이어그램으로 작성한다.
4. RE-03: 더블클릭·상위·뒤로/앞으로·새 탭·선택·이름 변경·검색의 이벤트와 내부 로직 연결을 추적한다.
5. RE-04: 아이콘/썸네일·연결 앱·변경 감지·복사/이동·DnD·속성·휴지통의 Windows API 재사용과 자체 로직을 구분한다. 예시 기능의 적용 여부·분석 불가도 기록한다.
6. RE-05: 각 주장에 질문, 함수 주소/ID, 참조·의사코드, 도구/엔진/대상 해시, 신뢰도와 미확인을 연결한다. 정적 근거가 실행 의미를 충분히 설명하지 못하면 원본 관찰과 대조하고 추론을 분리한다.
7. A에는 공통 실행파일·직접 관찰 자료만 전달하고 REA 자료는 B 영역에만 보관한다. 기능별 분류와 조사 질문 성공/실패 기록을 갱신한다.

게이트: P0 주요 동작마다 분석 자료 또는 구체적인 분석 불가 사유가 존재한다. 분석 불가 기록이 있다고 해당 기능 역공학 성공을 주장하지 않는다.

Phase 3 전달: P0/P1 동작 명세, 함수/호출 도식, 원본 관찰·REA Evidence 연결표, API 의존성, 미확인 의미·제약, A/B 공통 관찰 입력과 B 전용 근거의 분리 상태.

## Phase 3 — 아키텍처와 테스트 설계

1. Qt6 Widgets/QML을 UI 재현성·개발 난이도·성능/메모리·사용자 정의·크로스플랫폼·유지보수 기준으로 비교하고 하나를 ADR에 결정한다. 실측 없는 비교는 예상으로 표시한다.
2. Presentation/Application/Domain/Platform Interface/Adapter 책임과 의존성을 정의한다. UI·공통 비즈니스 로직·OS 종속 기능을 분리하고 경로/항목/기록/탭/검색/정렬/작업/진행/오류의 소유자를 정한다.
3. Windows Win32/Shell/COM은 Windows 어댑터에 둔다. Linux 표준 파일시스템/필요 시 GIO, macOS 표준 파일시스템/필요 시 Foundation/AppKit 경계를 설계한다. 공통 코어의 Win32 직접 의존을 금지한다.
4. 플랫폼 capability 질의·명시적 미지원 오류, 비동기 로딩/취소/수명주기, 파일 변경 경합·링크 순환·긴 경로/Unicode 정책을 계약으로 정한다.
5. 공통 코어 모의 어댑터 테스트, 실제 OS 통합 테스트, GUI 시나리오, 읽기/수정 fixture 분리, 14필수 시나리오, 원본 비교와 패키지 테스트를 설계한다.
6. 동일 조건 원본/A/B 비교용 데이터셋·환경·정답·판정·성능 기준을 사전에 고정한다. 외부 라이브러리/자산 라이선스, 포맷팅·정적 분석·CMake 재현 빌드·API 문서 책임을 정한다.

게이트: 모듈 구조와 정확한 공통/플랫폼 인터페이스가 확정되고 테스트 구조가 문서화되어야 한다. 설계 문서만으로 이식성/성능을 검증했다고 하지 않는다.

Phase 4 전달: ADR, 계층/모듈·인터페이스 계약, 테스트/fixture·A/B 프로토콜, 성능 목표/기준 환경, 기능별 근거/불명확 의미, 미해결 설계 위험.

## Phase 4 — P0 구현과 실제 검증

1. C++20/MSVC/Qt6/CMake 기반 구조를 만들고 재현 빌드한다. `src/ui`, `src/core`, `src/platform`, `include`, `tests`의 책임을 유지한다.
2. FR-01–10 전부: 기본 UI, 드라이브/폴더 탐색, 입력/더블클릭 이동, 뒤/앞/상위, 메타데이터, 세 정렬, 현재 폴더 이름 검색, 탭 생성/전환/닫기, 기본 연결 앱 실행, 오류 대응을 구현한다.
3. 상단 탭·탐색/주소·트리·목록·검색·상태 레이아웃, 키보드/마우스, resize·포커스·합법 자산, Unicode/긴 이름, 비동기·진행/복구 UX를 확인한다.
4. 공통 코어/모의 어댑터와 실제 Windows GUI/OS 기능을 따로 검증한다. 구현별 REA 근거·일반 API·AI 추론 분류를 갱신한다. 원본과 같은 fixture/절차로 동작을 비교한다.
5. P0 관련 필수 테스트를 실제 실행하고 로그·스크린샷·CPU/메모리·시간을 기록한다. 수정 관련 10/12 등의 미구현 검증은 미실행으로 남기고 Phase 5에서 반드시 다룬다. 14시나리오 전체가 통과했다고 성급히 주장하지 않는다.
6. A/B 각각 동일 요구 범위를 독립 구현하고 입력·컨텍스트·도구 사용을 통제한다. 실패/막힘도 실제 실험 결과로 보존한다.

게이트: P0 전체 기능 구현 및 실제 테스트 통과. P0 통과가 REA 근거 없는 기능의 역공학 성공이나 전체 프로젝트 완료를 뜻하지 않는다.

Phase 5 전달: 실제 빌드/실행·P0 테스트·원본 비교, 기능 기여표, UI 자료, A/B 산출물/측정, 남은 P1/P2·실패/성능·플랫폼 문제.

## Phase 5 — P1 확장·UI 개선·이식성

1. FR-11–20 전부를 대상으로 복사·이동/충돌·휴지통/안전 삭제·이름 변경·폴더 생성·Ctrl/Shift 다중선택·내부/OS DnD·세 보기 모드·단축키·개수/선택/진행률을 구현하고 실제 시험한다.
2. 격리된 수정 suite에서 충돌·권한/잠금·이름 변경 실패·부분 복사 실패·원본 보존·확인 취소·외부 삭제·링크 순환을 검증한다. 필수 14시나리오 전체의 원본/재구현 비교와 제한을 완성한다.
3. Windows 11 스타일 참고 UI를 개선하고 원본/재구현 동일 시나리오 스크린샷과 주요 기능 실제 시연 자료를 만든다. 기능 동작 복원과 디자인 선택을 혼동하지 않는다.
4. OS 종속 호출·헤더·링크의 어댑터 경계, capability·Unsupported 오류, 모의 코어 테스트를 감사한다. Linux 빌드를 실제 시도하고 환경·명령·결과·공통/어댑터 테스트·제한을 기록한다. 환경 확보 시 실행한다. macOS는 공통 코드 호환성을 검토하고 환경 확보 시 실제 실행하며 미검증을 표시한다.
5. Windows 실행파일과 Qt 배포 의존성을 포함한 패키지를 준비해 실제 실행한다. 재현 빌드·README/API 문서·포맷/정적 분석·외부 라이선스를 완성한다.
6. P2 10항목을 각각 분석 가능성/시간 기준으로 결정한다. 구현한 것만 검증하고 미구현 항목을 남긴다. P1 실패·미완료도 숨기지 않는다.
7. 초기 구현과 초기 분석 보고서, A/B 산출물·입력·테스트/측정·주장 목록을 소스 열람 전에 고정한다. 커밋·파일 해시·시간·빌드/모델/세션·원본 소스 미접근 범위와 한계를 manifest로 남긴다.

운영 게이트: P1 전체 대상의 실제 상태/시험·미완료 공개, UI·경계 감사, Linux 빌드 시도와 실행 여부/결과, macOS 검토, Windows 패키지 실행 증거, 초기 구현·분석 freeze가 준비되어야 한다. 명세에 별도 Phase 5 완료 문장은 없으므로 이 게이트는 명시 작업의 누락 방지용이다.

Phase 6 전달: freeze manifest, A/B 비교 입력/결과, Windows 앱·패키지, 전체 기능/14테스트/플랫폼 상태, 초기 분석 주장과 Evidence, 측정 원자료, 남은 문제·P2 미구현 목록.

## Phase 6 — 최종 소스 검증과 정량 평가

최종 소스 접근 전 게이트:

- 초기 구현과 분석 보고서가 고정되었고 정확한 커밋/해시·시간이 기록되어 있다.
- A/B 각 소스 비공개 실험 산출물과 입력·컨텍스트·도구 사용 기록이 고정되어 있다.
- 최종 검증 전에는 원본 소스 접근이 없었다는 증거와 통제의 한계를 기록했다.
- 별도 검증 디렉터리와 실제 접근 권한이 준비되어 있고, 사후 자료가 초기 결과를 소급 변경하지 않는다.

이 조건이 충족된 뒤에만 고정한 배포 버전에 대응하는 원본 소스를 별도 검증 영역에서 확인한다. 버전 대응이 불분명하면 정확도 검증의 한계로 남긴다. 의사코드를 원본 코드와 동일시하지 않는다. 처음부터 원본 구현을 복사해 대체하지 않는다.

1. 기능마다 REA 함수/호출·직접 관찰·재구현 결과·원본 소스 구조의 4방향 비교를 작성한다. 확인/오류/미확인과 분석 실패 이유를 분리한다.
2. A/B 동일 테스트의 기능 구현률·동작 일치율·안정성·이식성·실제 개발 시간·분석 성공률을 계산한다. 모델·입력/출력 토큰·실제 API 비용·리소스를 비교하고 미측정·추정·환경 차이·컨텍스트 오염을 공개한다.
3. 원본/A/B의 동일 조건 성능을 cold/warm별로 비교한다. 아직 측정하지 못한 CPU/메모리·분석 엔진·패키징/부팅 비용을 결과에 명시한다.
4. 기술적 한계/실패, 남은 문제·미구현, 모델/리소스 보고서, 주요 기능 시연·UI 비교, 최종 README와 요구사항 추적표를 현재 결과로 갱신한다.
5. §13 최종 11기준과 §1–12의 모든 명시 항목·산출물·14시나리오·6단계 작업을 실제 파일/출력/실행 결과로 감사한다. 미완료·미검증·간접 근거는 완료로 간주하지 않는다.

운영 게이트: 실제 REA/Ghidra 분석 및 clean-room 기록, Windows C++20/Qt6 빌드/실행·P0 전체 통과, 주요 원본 비교, 계층 분리·공통 이식성·Linux 여부/결과, 실제 A/B/사후 소스 평가, 모델/시간/리소스/비용과 모든 한계를 보고해야 한다. 전체 명세의 의무가 증명되어야 완료를 선언한다. P2 선택 미구현과 조건부 OS 검증 불가는 명세대로 명확히 기록한다.
