# REA 효과 비교 실험 프로토콜

기준: [`../requirements.md`](../requirements.md) §9–10, [`requirements-matrix.md`](requirements-matrix.md), [`../plan.md`](../plan.md). 최초 계획 2026-10-21, 진행 상태 갱신 2026-10-22 Asia/Seoul. Phase 2 자료·미확인 게이트와 Phase 3 계약 확정 후 A/B 각각 P0 구현·테스트를 진행 중이다. 아래 이상적인 통제 계획과 실제 확보한 조건의 차이를 구분한다.

## 실험 조건과 격리

| 조건 | 실험 A | 실험 B | 현재 검증 |
|---|---|---|---|
| 모델 | 親 세션 모델·reasoning 상속, override 없음 | 親 세션 | 라우팅 설정 상속만 확인; 정확 배포 ID·동일 가중치 검증 불가 |
| 설정 | fresh-context, REA/B 입력 금지 | REA 분석 컨텍스트 보유 | 샘플링/compaction·백엔드 설정은 접근 불가 |
| 기능 범위 | FR-01–20 전체, P2 선택 | 동일 | 현재 P0; P1을 제거하지 않음 |
| 시간/기능 예산 | 필요한 전체 범위를 완료하는 방식; hard deadline 없음 | 동일 | 활성 토큰/시간을 같은 수치로 제한하지 못했으므로 통제된 생산성 인과 비교에는 한계 |
| 공통 입력 | 요구사항, 공식 원본 EXE, 순수 UI 관찰, fixture, 실제 Win11 참고 화면 | 동일 | A/inputs 초기 hash manifest; 후속 관찰 OBS015–019는 양측 공유, 구현 중 입력 추가를 기록 |
| REA | 도구·분석 출력·B 코드/설계/메모 접근 금지 | 실제 REA/Ghidra Evidence | A /root/experiment_a fresh-context 세션; 도구별 강제 차단 없음 |
| 원본 소스 | 초기 구현·보고서 freeze 전 금지 | 동일 | verification/source 실제 NTFS 읽기 거부, 소스 다운로드·열람 없음 |
| 환경 | 같은 호스트·fixture·Qt/MSVC/공유 빌드 runner; Linux 기존 Qt | 동일 | environment-audit 및 qt-setup 실측 기록 |

A는 새 컨텍스트의 독립 세션에서 시작한다. 이 프로젝트의 REA 분석 자료를 이미 읽은 세션을 A로 재사용하지 않는다. A가 허용받는 프로젝트 입력은 공식 원본 배포물, 요구사항, 공통 직접 UI 관찰, 동일 합성 fixture뿐이다. OS/Qt/C++/CMake 등 허용된 공식 API 문서는 양쪽에 같은 규칙으로 허용하고 URL·사용 목적을 기록한다. Explorer++ 원본 C++ 코드·클론·코드 검색·기존 구현 복사·근거 없는 공개 역공학 자료는 양쪽 모두 금지한다.

공유 UI 관찰은 원본을 실제 조작해 얻은 동작·화면·조건만 담고 함수 이름·주소·import·의사코드·REA 유래 의미를 넣지 않는다. A는 별도 작업 디렉터리·fresh-context·허용 입력 지침으로 분리했다. 같은 Windows 사용자이므로 A/B 사이 강제 ACL 격리와 도구 차단은 확보하지 못했다. 이 결과를 완전히 통제된 독립 인과 실험으로 주장하지 않는다. root는 B 구현 확정 전 A 소스/설계를 열지 않으며 A의 상태·측정 메타데이터만 받는다.

최초 계획은 모든 입력·시간 예산의 사전 고정이었다. 실제로 원본 hash·fixture·요구 범위·허용 자료는 공유했지만, 공통 관찰을 구현 중 보충했고 정밀 활성 시간/과금·고정 시간 상한은 확보하지 못했다. A/B 구현 산출물과 개별 검증은 비교할 수 있어도 REA만의 효과라는 인과 결론은 제한한다. 기능/필수 시험 범위는 양쪽 FR01–20·14시나리오를 유지한다.

REA 전용 입력 확보·Ghidra 분석·Evidence 탐색/정리의 시간·AI 사용량·CPU/메모리를 구현 시간과 별도로 기록한다. 구현·검증에 배정하는 기능/시간 예산은 양쪽에 동일하게 적용하고, 최종 생산성 비교에는 B의 REA 선행 비용을 포함한 총비용도 함께 제시한다. 공통 원본 확보·공유 관찰·fixture 준비는 공통 비용으로 별도 기록하고 임의로 B 또는 A에만 부담시키지 않는다. REA 없이 수행할 수 있는 공통 준비와 REA 전용 조사를 구별한다.

## 결정론적 fixture

생성기: [`../../scripts/create_fixtures.py`](../../scripts/create_fixtures.py). Python 표준 라이브러리만 사용하며 실행 위치와 무관하게 프로젝트의 `test-data/fixture-v1`만 대상으로 한다.

```powershell
python scripts/create_fixtures.py
python scripts/create_fixtures.py
python scripts/create_fixtures.py --check
```

| 입력 폴더 | 목적 |
|---|---|
| `read-only/empty` | 빈 폴더/0개 상태 |
| `read-only/bulk` | 정확히 1,200개 파일; 알려진 길이·SHA-256·UTC 수정일; 크기/날짜 동률 |
| `read-only/unicode` | 한글·공백·허용 특수문자·é·emoji·긴 이름 |
| `read-only/navigation` | 중첩 이동·뒤/앞/상위·독립 탭 |
| `read-only/errors` | 정상 읽기 파일과 반드시 존재하지 않는 경로의 부모 |
| `mutation/collision/source`, `destination` | 같은 이름/서로 다른 내용과 단일·복수 복사/이동 충돌 |
| `mutation/rename` | 이름 충돌 실패 후보의 서로 다른 두 파일 |
| `mutation/external-change` | 외부 삭제/변경용 기준 파일 |

`manifest.json`은 파일별 상대경로, 바이트 길이, SHA-256, 정확한 UTC 수정 시각과 폴더 목록을 보존한다. `manifest.sha256`은 manifest 자체의 해시이다. JSON은 UTF-8이며 원래 한글·Unicode를 보존한다. 생성기는 고정 콘텐츠와 시각만 사용하고 현재 시각·난수·절대경로를 manifest에 넣지 않는다. 생성/디렉터리 시각·OS별 파일 형식 표시·권한은 고정했다고 주장하지 않는다.

`expected`에는 즉시 자식 목록, bulk의 이름/크기/수정일 오름차순 정답, 동률 규칙, 현재 폴더의 casefold literal 부분문자열 검색 정답을 저장한다. `FILE-00`은 100개 이름, `한글`은 실제 한글 파일 이름 집합, 없는 이름은 빈 집합을 기대한다. 합성 비교 규칙은 테스트 oracle이며 Explorer++에서 역공학으로 확인한 정렬·검색 정책이 아니다. 원본 관찰로 실제 정책을 확정하고, 정책이 다르면 원시 파일 사실을 유지한 채 비교 판정을 별도로 정의한다. 특히 locale/natural sort, 동률, 확장자 표시, 날짜 표시 timezone·검색 패턴 의미를 추측하지 않는다.

생성기는 소유 marker를 사용하며 예상 밖 기존 항목, 수정된 내용/완성 fixture 시각·manifest, 링크/reparse point를 만나면 실패한다. 기존 파일을 덮어쓰거나 삭제하지 않는다. 새 파일은 exclusive create로 만들고 이미 올바른 파일은 그대로 재사용한다. 초기 생성이 중단되어 owner만 있고 manifest/checksum이 모두 없으면, 전체 기존 트리가 예상 파일명·내용과 일치할 때만 기존 파일의 미완료 수정 시각을 완성한다. 이 경우도 내용을 쓰거나 교체하지 않으며 실행 결과에 복구 수를 남긴다. 생성 중 외부에서 같은 폴더를 변경하지 않는 단일 writer 조건을 사용한다. 실패 후에는 원인을 기록하며 자동 삭제·재생성으로 덮어 감추지 않는다.

`read-only/`는 읽기 테스트 분리 이름이며 OS 권한 거부 설정이 아니다. ACL, permission bit, read-only attribute를 변경하지 않고 symlink/junction도 만들지 않는다. 실제 접근 거부·잠금·순환 링크·플랫폼 한계를 넘는 경로는 이 fixture만으로 검증할 수 없다. 이 항목은 별도 안전한 환경·필요 승인·실제 실패 증거가 생길 때까지 미검증이다. 긴 이름은 169자 ASCII 파일명으로 일반 컴포넌트 제한 안에 두며, 이것만으로 Windows 장경로 지원을 주장하지 않는다.

수정 테스트는 기준 fixture를 직접 파괴하지 않고 별도로 소유한 disposable copy에서 실행한다. 복사 위치·원본 fixture hash·쓰기 범위를 고정하고 쓰기/삭제/overwrite 승인을 별도로 확인한다. 복사/이동/이름 변경 성공·실패 후 원본·대상 내용 해시를 비교한다. 생성기는 수정된 fixture를 자동 복구하지 않는다.

생성·재실행 검증 결과는 아래 실행 기록에 실제 값만 추가한다. 이 문서 작성 시점에는 A/B 결과가 없다.

## 시험·측정과 기록 양식

필수 14시나리오는 [`requirements-matrix.md`](requirements-matrix.md)의 T-01–14 전부이다. 읽기와 수정 suite를 분리하고 각 시나리오에서 원본/A/B의 동일한 입력·절차·환경을 사용한다. 코드 존재나 테스트 이름만으로 통과시키지 않는다. UI 화면·선택/포커스·오류·진행률·종료·파일 해시처럼 해당 요구를 직접 증명하는 결과를 남긴다.

| 기록 단위 | 필수 정보 |
|---|---|
| 실험 세션 | A/B, 실제 모델 식별자/설정·세션 ID, 허용 입력·권한, 시작/종료·중단, 원본/fixture/코드 해시, 환경·명령 |
| 기능 | FR/P2 ID, 구현 상태, 실제 테스트, 원본 일치/차이, 기여 분류와 Evidence, 미검증/미지원 |
| 분석 질문 | 조사 목적, 성공 기준, 실제 함수/호출/의사코드 Evidence, 신뢰도·실패/불명확 이유 |
| 시험 | T ID, 플랫폼·빌드/패키지, fixture hash, 기대/실제 결과, 명령/조작·로그/캡처, 통과/실패/미실행 |
| 측정 | 단계·task ID, cold/warm, elapsed·CPU·peak process-family memory, 측정 도구·프로세스 집합·샘플 간격, 반복/대기·예외 |
| AI 비용 | 모델/가격 기준·통화, 실제 입력/출력 토큰 및 제공되는 cache/reasoning 구분, API 비용 원자료, 추정/미측정 |

파일별 출력 크기나 문서 길이를 토큰 사용량으로 환산해 실측이라고 주장하지 않는다. 모델/토큰/가격/비용 접근이 불가능하면 `미측정(접근 불가 이유)`로 남긴다. 추정 비용은 실제 비용과 별도 표에 계산 근거·불확실성을 표시한다. 이미 기록하지 못한 작업 시간을 정밀하게 소급하지 않는다.

elapsed는 같은 시나리오 시작→사용 가능한 완료/실패까지 측정하고 UI 응답성을 별도로 기록한다. CPU는 wall time과 구별하며 프로세스/자식 수명주기 전체를 집계한다. peak process-family memory는 시점별 관련 프로세스 메모리 합의 최대값이며 서로 다른 시점의 개별 peak 합을 전체 peak로 부르지 않는다. 빠르게 종료한 자식/측정 사각지대·Ghidra/JVM·IDE·에이전트 포함 여부를 명시한다. 측정할 수 없는 프로세스나 단위는 미측정이라고 쓴다.

cold/warm은 앱 새 실행/분석 cache/OS 파일 cache를 구분한다. OS cache를 비우지 않았으면 `cold OS cache`라고 부르지 않는다. warm은 같은 입력의 사전 실행·cache 유효성을 확인한 뒤 측정한다. 단순 연결 응답 시간과 전체 분석·개발 task 비용을 섞지 않는다. 환경/데이터셋을 고정한 사전 테스트 후 성능 기준을 확정하며 결과에 맞춰 목표를 소급 변경하지 않는다.

계산식은 기능 구현률 = 실제 통과 기능/고정 요구 기능, 동작 일치율 = 원본과 일치한 비교 시험/고정 비교 시험, 분석 성공률 = 필요한 근거를 확보한 조사 질문/사전 조사 질문, 안정성 = 실제 통과 예외 시험/고정 예외 시험이다. P0/P1/P2·미실행·미지원·제외 항목을 분리해 분모를 숨기지 않는다. 이식성은 OS별 실제 빌드·실행·공통/어댑터·패키지 결과를 표로 기록한다.

## 최종 소스 검증 게이트

초기 분석 보고서·구현·A/B 입력/산출물·주장 집합·시험/측정 결과를 커밋/해시·시각으로 고정한 manifest가 있어야 한다. 검증 디렉터리는 이 게이트 전까지 비워 두고 원본 소스를 내려받거나 컨텍스트에 넣지 않는다. 디렉터리/실제 읽기 권한을 분리한 후에만 배포 버전 대응 소스를 최종 검증 세션에서 확인한다.

기능마다 REA 함수/호출, 원본 동작 관찰, 재구현 결과, 최종 소스 구조를 대조한다. 의사코드를 원본과 동일하게 취급하지 않고 최적화·추정 타입·버전 차이와 미확인을 표시한다. 사후 소스 지식을 초기 clean-room 정확도에 소급 반영하지 않는다. REA 근거 기반/일반 API 기반/AI 추론 기반/미구현을 구분하고, Qt 모델만 사용한 기능을 REA 복원 성공이라고 주장하지 않는다.
